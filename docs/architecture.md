# OpenThreatGrid Architecture

OpenThreatGrid is a Kubernetes-native honeynet and threat intelligence platform. It collects attack telemetry from honeypot sensors, normalizes the data, stores it, visualizes it, and generates intelligence reports.

## High-level Architecture

```text
Internet
   |
   v
+-----------------------+
| Honeypot Sensor Layer |
| - Cowrie              |
| - Dionaea             |
| - HTTP trap           |
+-----------------------+
   |
   v
+-----------------------+
| Filebeat (sidecar)    |
| - Tail sensor log     |
| - Handle rotation     |
| - Ship to Logstash    |
+-----------------------+
   |
   v
+-----------------------+
| Logstash              |
| - Normalize to schema |
| - Enrich + GeoIP      |
| - Output to OpenSearch|
+-----------------------+
   |
   v
+-----------------------+
| Storage Layer         |
| - OpenSearch          |
|   (otg-events-*)      |
+-----------------------+
   |
   +---------------------> OpenSearch Dashboards
   |
   +---------------------> Weekly Report Generator
   |
   +---------------------> Threat Hunting Queries
```

## Component Overview

### 1. Honeypot Sensor Layer

The sensor layer contains one or more honeypots exposed to the internet. The MVP starts with Cowrie because it is useful for collecting SSH and Telnet brute-force activity.

Initial sensor:

- Cowrie SSH/Telnet honeypot

Future sensors:

- Dionaea for malware delivery attempts
- Conpot for ICS-style telemetry
- Honeytrap for multi-protocol traps
- Custom HTTP fake login honeypot

### 2. Filebeat (log shipper)

A Filebeat sidecar runs in every sensor pod (Apache-2.0 `filebeat-oss:7.12.1`).
It tails the sensor's JSON log, handles rotation/truncation/checkpointing
natively, and ships each raw line to Logstash with a `log_type` field selecting
the sensor.

### 3. Logstash (normalize + enrich)

A single Logstash pipeline (`logstash-oss:7.12.1` + `logstash-output-opensearch`)
branches on `log_type` and converts each sensor's records into the normalized
OpenThreatGrid event schema, then writes them to OpenSearch.

Responsibilities:

- Map sensor-specific fields into the common schema (eventid/logtype → `event_type`).
- Tag events and detect botnet-command indicators (mirrors the OTG enrichment).
- GeoIP enrichment (`geo_country`; ASN optional).
- Idempotent output (`action => create`, `_id = event_id`) to `otg-events-*`.

The pipeline lives in
[`deploy/filebeat-logstash/logstash/pipeline/otg.conf`](../deploy/filebeat-logstash/logstash/pipeline/otg.conf);
see [Filebeat + Logstash](filebeat-logstash.md).

### 4. Storage Layer

OpenThreatGrid is OpenSearch-native. Events are written to daily indices under
`otg-events-*` governed by an index template (string fields that drive
aggregations are mapped as `keyword`, `source_ip` as `ip`). The API creates the
template automatically on startup; the canonical copy lives in
`opensearch/index-templates/otg-events.json`.

Document `_id` is the event's `event_id` and writes use the `create` op type, so
a worker can safely retry a batch — duplicates raise a 409 conflict and are
reported as "not accepted" instead of overwriting telemetry.

### 5. Dashboard Layer

The dashboard layer uses **OpenSearch Dashboards**. The index pattern, shared
visualizations, and the eight dashboards from plan §10 are version-controlled as
saved objects (`opensearch/dashboards/otg-dashboards.ndjson`, generated by
`build_saved_objects.py`) and imported automatically by the deploy bootstrap:

- **Threat Overview** — totals, events over time, top IPs/countries/usernames/passwords/commands.
- **Cowrie SSH/Telnet Activity** — SSH vs Telnet over time, credential pairs, commands, payload URLs.
- **Credential Abuse** — login/root/admin attempts, unique creds per source IP, attempts over time.
- **Threat Hunting** — suspicious (botnet-tagged) commands, payload attempts, tag distribution.
- **Malware & Payload** — payload attempts over time, top URLs, by IP/sensor, download commands.
- **Source IP Intelligence** — top IPs, country/ASN breakdown, creds & payloads per IP.
- **Sensor Health** — active sensors, events & last-event per sensor, ingestion rate.
- **Executive Summary** — totals + top-5 breakdowns and weekly trend for non-technical readers.

Panels that need scoping carry a KQL query (e.g. `protocol:"ssh"`,
`event_type:"file_download"`, botnet `tags:(...)`). Operational metrics named in
the plan (parser/API errors, queue depth, CPU/disk) are out of scope here — they
belong to a Prometheus/ops stack, not the event store.

### 6. Report Generator

The report generator creates weekly Markdown reports from stored telemetry.

Report output:

- `reports/generated/YYYY-WW-weekly-threat-report.md`

Possible future output:

- HTML report
- PDF report
- GitHub release note
- Blog post template

## Security Architecture

Core safety controls:

- Dedicated namespace for honeypot workloads.
- NetworkPolicy to restrict outbound traffic.
- Separate service accounts.
- No access to production secrets.
- No shared hostPath unless strictly required.
- Raw malware binaries disabled by default.
- Dashboard exposes aggregated data only.

## Data Flow

1. Attacker connects to a sensor (e.g. Cowrie).
2. The sensor writes a raw JSON event log.
3. The Filebeat sidecar tails the log and ships the line to Logstash.
4. Logstash normalizes, tags, enriches (GeoIP), and indexes the event into OpenSearch.
5. Dashboards query aggregated statistics from OpenSearch.
6. The report generator reads OpenSearch and creates weekly intelligence output.

## MVP Design Decision

OpenThreatGrid intentionally starts small:

- One sensor type.
- One event store (OpenSearch).
- One dashboard.
- One report generator.

This keeps the solo developer scope manageable while still demonstrating a complete cybersecurity platform.
